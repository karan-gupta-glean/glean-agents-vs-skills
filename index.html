Design the system, not just the prompt.

Agents and Skills solve different layers of work. This guide gives builders, operators, and leaders one shared vocabulary for choosing, building, testing, and governing both.

The shortest useful distinction: a Skill packages reusable expertise for a task; an Agent orchestrates an end-to-end workflow from trigger to outcome. Many production solutions use both.

Start with the mental model

Two layers of the same automation stack.

Do not ask which product is “better.” Ask whether you are packaging how to perform a task, orchestrating when and how a process runs, or doing both.

Choose intentionally

Let the work—not the hype—choose the form.

Answer four questions. The recommendation updates as you go and explains the architecture to start with.

1. What is the durable value?
2. How should it start?
3. How much orchestration is required?
4. Should the expertise be reused elsewhere?
Recommended starting point

Start with a Skill

Package the method once, make its routing precise, and test the quality of the task output.

  • Define one clear job and output contract
  • Write a specific name and routing description
  • Add examples, references, or templates only when useful

Important: identity, permissions, or a write action alone do not automatically make something an Agent. Choose based on orchestration and lifecycle needs, then add the security controls appropriate to the risk.

Use proven patterns

Three architectures cover most use cases.

Start with the smallest architecture that can reliably own the outcome. Extract reusable expertise instead of copying it between workflows.

Skill only

Reusable expertise on demand

Best when a person or Assistant remains in control and needs a consistent method, structure, or standard.

Request → route Skill → apply method → result
  • Account plan using your sales methodology
  • Contract review against approved criteria
  • Executive brief in a standard format
  • Brand-voice rewrite with examples
Agent only

Purpose-built orchestration

Best when the value is the workflow itself and no broadly reusable domain package is needed yet.

Trigger → gather → decide → act → report
  • Route incoming requests by category
  • Monitor a source and escalate exceptions
  • Coordinate approvals across systems
  • Run a tightly scoped team utility
Agent + Skill

Orchestration powered by reusable expertise

Best for production workflows that should apply the same method in the Agent, Assistant, or future automations.

Trigger → Agent → Skill + tools → governed outcome
  • Monthly report using a research methodology Skill
  • Support triage using a response-quality Skill
  • Sales follow-up using a brand and MEDDPICC Skill
  • Onboarding workflow using role-specific checklists

Anti-pattern · The mega-Skill

One Skill claims every task, routes too often, and carries a wall of instructions. Split by stable job and keep descriptions discriminative.

Anti-pattern · The prompt-shaped Agent

An Agent exists without a clear trigger, process owner, measurable outcome, or operating plan. Use a Skill or Assistant prompt until orchestration is justified.

Anti-pattern · Copy-pasted expertise

The same policy lives in multiple Agent prompts. Extract it into a shared Skill or governed reference so updates happen once.

Anti-pattern · Autonomy before safety

A broad audience receives write-capable automation before permission testing, UAT, approvals, monitoring, or rollback exists.

Build for production

Quality comes from design choices, not longer prompts.

Use these playbooks as review criteria. Each item makes behavior easier to understand, test, maintain, and govern.

Skill design playbook

Make expertise easy to route, apply, and maintain.

8 checks
  1. 01

    Give it one recognizable job

    Name the task and audience. Split unrelated jobs rather than creating a universal Skill.

  2. 02

    Engineer the description for routing

    Say what it does, when it applies, key terms users will say, and when it should not run.

  3. 03

    Define the output contract

    Specify required sections, format, evidence, tone, and acceptance criteria—not hidden assumptions.

  4. 04

    Use progressive disclosure

    Keep core instructions concise; move deep references, templates, and examples into supporting files.

  5. 05

    Show decisions and edge cases

    Provide examples, counterexamples, fallbacks, and conditions that require clarification.

  6. 06

    Use scripts for deterministic work

    Prefer a tested helper for exact transformations or calculations; use language for judgment.

  7. 07

    Test both routing and execution

    Check explicit invocation, automatic matches, false positives, realistic inputs, and output quality.

  8. 08

    Assign source, owner, and review cadence

    Track where the Skill came from, who maintains it, and when its standards need review.

Agent design playbook

Make workflows safe, resilient, and operable.

8 checks
  1. 01

    Start with value and a measurable outcome

    Define the business problem, target users, baseline, success metric, and non-goals before building.

  2. 02

    Map trigger → steps → outcome

    Document inputs, decisions, tools, branches, expected outputs, and stop conditions.

  3. 03

    Choose flow versus auto mode deliberately

    Use explicit flow for predictable control; dynamic planning where the path must adapt.

  4. 04

    Apply least privilege

    Limit tools and knowledge to what the job needs. Separate read and write risk and verify user profiles.

  5. 05

    Design human checkpoints

    Require review or confirmation before consequential, external, ambiguous, or hard-to-reverse actions.

  6. 06

    Handle failure explicitly

    Plan for missing data, tool errors, duplicate events, partial completion, timeouts, retries, and escalation.

  7. 07

    Evaluate with a golden set and UAT

    Test expected, edge, adversarial, and permission cases; involve the people who will use it.

  8. 08

    Operationalize ownership

    Publish purpose, examples, limits, support path, maintainer, version plan, monitoring, and rollback.

Before a write action

Treat writes differently from reads, especially for external communications and irreversible changes.

  • Confirm destination and payload
  • Use least-privilege credentials
  • Add human approval where impact warrants it
  • Test failure and duplicate execution

Before broad sharing

Distribution increases both value and blast radius. Validate with a representative cohort first.

  • Start restricted, then expand
  • Test with restricted user profiles
  • Document purpose and non-goals
  • Identify owner and support path

After launch

A production asset is managed, not merely published. Watch behavior as data and workflows change.

  • Monitor adoption and quality
  • Review feedback and failed runs
  • Audit sharing and ownership
  • Version changes and retain rollback
⚠

Configuration varies by tenant and rollout. Confirm enabled features, roles, supported triggers, identity options, and policy availability in your Admin Console and current documentation before making a control claim.

Clarify the edge cases

Questions teams ask next.

Use these answers to align builders, admins, security partners, and business owners before implementation.

Is a Skill just a smaller Agent?

No. A Skill packages reusable expertise for a task; an Agent owns orchestration from trigger to outcome. A Skill may include instructions, templates, references, scripts, and tools, but it does not become an Agent merely because it is sophisticated.

Does every Agent have its own service account?

No. By default, a Glean Agent runs under the identity and permissions of the user who invokes it. A distinct Agent identity is an optional administrative design for supported use cases that need a recognizable or separately bounded principal.

Does enabling a Skill grant access to more company data?

No. Skills operate within Glean's existing permission model and do not grant new data access. They guide how allowed information and tools are used.

When should a Skill become an Agent?

When the durable value shifts from “apply this method when asked” to “own this end-to-end process”—especially when triggers, multiple steps, branching, tools, operational monitoring, or a formal release lifecycle become necessary.

When should an Agent's logic become a Skill?

Extract logic when the expertise is useful outside one Agent, changes on its own cadence, should be governed once, or is being copied into multiple prompts. Leave process-specific wiring in the Agent.

Should every consequential action require human approval?

Not necessarily. Match human checkpoints to impact, reversibility, ambiguity, external exposure, and confidence. Automate low-risk, well-tested actions; require review for material or hard-to-reverse decisions.

How do we know an Agent is production-ready?

It has a clear owner and outcome, passes a representative golden set, handles edge and adversarial cases, respects permissions across user profiles, completes UAT, documents purpose and limitations, launches in stages, and has monitoring plus rollback.

Can everyone create and share Agents and Skills?

It depends on tenant configuration. Skills must be enabled; users can create personal Skills, while sharing scopes are admin-controlled. Agent creation, publishing, and sharing are separately configurable through member permissions and roles.

What is the best first use case?

Choose a high-frequency, painful workflow with clear inputs, a bounded audience, accessible data, an accountable owner, and a measurable baseline. Avoid beginning with the broadest or most sensitive process.
